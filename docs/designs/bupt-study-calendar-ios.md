## 1. 产品定位与目标

面向备考北邮信通院、电子院的本科生，提供以产品内学习日历为入口的规划、时间安排、行动指导、学习记录与复盘服务。

核心体验：学生通过语音表达进展、困难和时间约束，Agent 理解后生成具体任务及次日时段安排；学生确认后，App 自动保存到学习日历并设置提醒，省去逐项填写。

第一阶段成功标准是完整跑通功能闭环。真实用户试用、使用效果反馈安排在闭环跑通之后；付费真人一对一辅导为后续方向。当前没有对留存、付费或提分效果作出验证结论。

## 2. 已有需求依据与现状

- 用户本人已考研上岸，亲历备考初期迷茫、四处搜集信息。
- 多位学弟在备考初期和中期主动向用户咨询，说明规划与指导问题在这些具体关系中存在。
- 论坛、小红书等平台的经验帖与咨询是补充线索；帖子数量尚不能直接推导 App 的实际使用规模。
- 已知替代做法包括自行找资料和向学长咨询；其具体耗时、现有工具与操作路径尚未量化，本轮不继续做用户研究。

## 3. 已确认的设计决策

1. 独立 iOS App，采用 B 方案：产品内学习日历为主要入口，同时承担每日任务本与学习日记的作用。
2. 语音和 Agent 自动落地计划是核心能力，学生确认后才写入日历并设置提醒。
3. 完成反馈细分到具体任务和子任务，保留完成量、剩余内容及困难。
4. 未完成任务保留记录；Agent 根据阶段目标、任务优先级与可用时间重排，说明延期内容，经学生确认后更新日历。
5. 先开发并跑通流程，再寻找真实用户试用。系统日历主入口方案 A、双日历同步方案 C 本轮未采用。
6. App 打开后先显示本月月历；点击今天的日期进入今日任务页，采用 D14-B 的课程表式纵向时间轴，将一天分为固定的几段时间，按时段展示任务和完成情况，点击每个时段可查看详情。
7. 日常使用时，明日计划在完成今日总结后才生成；首次使用按 D4-A 直接生成首份日计划。漏做昨日总结且今天没有日计划时，按 D6-A 快速补充复盘后生成今天剩余时段。
8. 采用 D2-A：月计划明确阶段成果，周计划拆为具体学习任务及工作量，形成任务池；日常完成今日总结后，Agent 从剩余任务中安排明日时段。首次月/周计划按 D4-A 由产品生成，跨周时按 D12-A 随每日复盘提出新周任务池草案，跨月时按 D13-A 随复盘提出下月目标草案；均由学生修改或确认后应用。
9. 采用 D7 用户指定方案：语音反馈结束后，直接展示语音结构化处理后的文本内容，用户可直接修改结构化文本并确认；确认后保存对应记录。确认流程不要求核对识别原文。整份日计划仍需独立预览和确认后才写入日历。
10. 任务完成反馈支持已完成、未完成并记录原因、部分完成等状态，同时支持语音反馈。已有明确总量的任务按 D20-A 在部分完成时当次记录已完成数量，再计算剩余量；打卡未完成时按 D21-A 当次用文字或语音说明原因后保存。语音与已有打卡不一致时，按 D8-A 标出差异，用户修改或确认后更新；未打卡仍按 D6-A 保持待确认。
11. 采用 D3-A：底部设置独立“计划”入口，与“日历”并列；按 D22-A 在同页以本周任务池为主体、简要呈现本月目标。打开 App 后仍先显示月历。本稿的已批准导航为上述两个入口，未定义的其他导航不计入实施任务。
12. 采用 D4-A：用户首次提供报考目标、学习现状、相关背景和可用时间；产品据此生成月目标与周任务，用户可修改并确认。随后选择从今天剩余时间或明天开始，产品生成首份日计划供预览、修改和确认，确认后保存日历并设置提醒。首次启动无需先完成一份 App 内的今日总结，不虚构今日执行记录。
13. 采用 D5-A：未来尚未生成日计划的日期也允许进入，显示“尚未生成日计划”，说明日常安排在前一天总结后生成，并提供“查看周任务”入口。该页面不预先填入未经生成、确认的日程。
14. 采用 D6-A：漏做昨日总结且今早没有今天的计划时，产品用已有打卡预填简短复盘；未打卡的任务标为“待确认”，不自动判为未完成。用户核对实际进度并补充今天可用时间，确认复盘后生成今天剩余时段的日计划草案；整份日计划仍需确认后才写入日历和设置提醒。保留昨日执行记录，不补排已经过去的时段。
15. 采用 D8-A：本次语音结构化反馈与同一任务的已有打卡不一致时，直接在结构化内容中标出原记录和本次反馈的差异；用户在同一页修改或确认后更新，以本次最终确认内容为准，保留历史记录。仅生成差异草稿时不改写已确认记录。
16. 采用 D9-A：已确认的日计划保存失败时，保留已确认草稿，显示失败原因和“重试保存”；由用户点击重试保存同一份计划。用户可先修改，修改后需重新确认。不得把失败显示成成功，重试不得重复生成时段和提醒。
17. 原设计 D10-A 的后台接续要求由 2026-10-22 用户直接修订（工程 D10）取代：首版 AI 整理/生成在当前页面及 App 前台完成，页面实时展示真实处理阶段和可面向用户展示的生成内容，完成后展示可修改的完整结果。提示用户生成期间保持 App 前台；离页、切后台、关闭 App 或断网时不保证继续，保留本地输入和已确认记录，返回显示中断并由用户重试，不自动应用流式残片。阶段展示须由实际事件触发，不伪造百分比或模型内部思考。
18. 保留 D11-B 的首版提示边界，并随前台流程调整：整理或生成完成后直接在 App 当前页面展示待确认结果，学生修改确认后应用；不做 AI 完成手机通知。已确认学习时段的本地提醒继续保留。
19. 采用 D12-A：每日复盘完成后，若接下来安排的学习日进入新周，产品根据累计进度、阶段目标和剩余任务提出下周任务池草案，说明遗留任务的安排；学生可修改并确认，确认后再衔接对应日计划。已确认的漏总结恢复也按所安排学习日衔接此流程。保留原周实际记录，取消草案时不替换已确认任务池。
20. 采用 D13-A：跨月时随复盘，根据本月实际进度和备考阶段提出下月目标草案；学生可修改并确认，确认后用于后续周任务安排。保留本月实际记录，取消月草案时保留原已确认目标及安排。若同次复盘同时跨月、跨周，按已确认的层级关系先确认月目标，再衔接周任务池及日计划，不以确认上层目标替代下层计划确认。
21. 采用 D14-B，并按用户补充具体化：今日任务页采用类似课程表的纵向时间轴，一天分为固定的几段时间，每个时段可点击查看对应任务详情；沿用任务完成量、剩余内容、困难与多状态反馈。段数与起止时间按 D15-A 的个人模板确定，不预设全体学生使用同一张时间表。
22. 采用 D15-A：产品根据学生的可用时间和固定安排提出个人时段模板，学生可调整并确认；确认后固定复用，Agent 按既有的首次规划、每日复盘及漏总结恢复流程安排对应任务。时段模板与每日具体任务分开，不因每日生成任务而自动改写已确认模板；当日可用时间变化沿用既有的核对、排程预览与确认规则。
23. 采用 D16-A，并加入用户补充：首版以 iOS 原生工具界面为基线，统一文字层级、标准组件和少量强调色；架构需方便后续设计变更。视觉定义集中管理，共用组件统一呈现，页面布局与排程、任务记录、确认保存及提醒逻辑保持清晰边界；仅改变外观或布局时，不要求改写上述业务规则或数据含义。工程 D2-A 已选择 Swift + SwiftUI，具体分层、模块接口与文件结构继续由工程评审落实。
24. 采用 D17-A：颜色用于当前选择、主要操作和完成状态，学科以文字区分；月历、课程表时段、任务详情及反馈沿用同一套颜色语义，不为不同学科建立各自的固定配色。具体状态的文字含义沿用已经确认的任务反馈规则。
25. 采用 D18-A：系统字体放大时，今日课程表的时段行随文字内容增高，完整显示任务名称和完成状态，页面支持纵向滚动；时段仍可点击进入详情。行高是呈现尺寸，个人模板中的学习起止时间仍按已确认安排解释。
26. D19 按用户要求排除：本轮不考虑屏幕朗读（VoiceOver），不继续设计其概览、焦点或朗读组织方式，也不增加对应实施任务。此范围决定不取消 D18-A 的系统字体放大布局、状态文字与纵向滚动规则。
27. 采用 D20-A：对已有明确总量的任务，打卡“部分完成”时，当次填写或从语音中提取并确认已完成数量，保存后据此计算剩余量。数量应对应任务的计量单位；数量缺失或有歧义时需补充、校正，不将“部分完成”状态本身换算为猜测的完成量。此数量要求不扩展到尚无明确总量的学习任务。
28. 采用 D21-A：学生主动打卡“未完成”时，当次用文字或语音说明原因后保存；语音输入仍沿用结构化文本可编辑、确认后保存的规则。缺少原因时明确提示补充并保留本次草稿，不将其显示为原因已齐全的已保存记录，也不凭空补写原因；未打卡任务仍按既有规则待确认。
29. 采用 D22-A：底部“计划”入口内同页展示本月目标与本周任务池，以本周任务池为主要内容，简要呈现本月目标作为上层方向；沿用已经确认的任务工作量、剩余进度及月 → 周 → 日的关系。此项确定内容组织，不增加新的独立业务功能。
30. 采用 D23-A：首版暂缓具体题目的讲解与解答，保留既有的备考规划、学习情况与困难交流、学习方法建议。该决定只缩减题目级学科答疑的范围，不取消基于垂类资料与个人情况的规划指导和交流。
31. 工程 D11-A：语音原音只在手机内识别为文字，不上传给自有后端、Apple 网络识别或其他第三方识别服务；云端大模型接收识别后的文字及必要学习上下文。必须先核验本机识别能力，不支持、授权拒绝或识别失败时提供既有文字输入，不隐式转用网络识别。直接展示结构化内容、用户修改确认的规则不变；具体设备、系统与中文识别效果尚未验证。

## 4. 已确认的功能闭环

| 环节 | 学生的动作 | 产品的交付 |
|---|---|---|
| 首次建档 | 语音或文字提供报考目标、学习现状、相关背景、可用时间与固定安排 | 可编辑的备考档案，以及需要补充的信息 |
| 建立方向 | 查看产品生成的月目标和周任务，可修改并确认 | 依据学生情况和垂类策略生成月度阶段目标与周任务池，确认后作为每日安排的参照 |
| 个人时段模板 | 查看产品根据个人可用时间和固定安排提出的模板，可调整并确认 | 形成固定复用的个人时段，供 Agent 安排每日任务；段数与起止时间随个人情况确定（D15-A） |
| 首份日计划 | 首次选择从今天剩余时间或明天开始，查看和调整首份日程 | 基于已确认的个人时段模板直接生成首份日计划草案；整份确认后保存日历并设置提醒，不要求先完成今日总结 |
| 每日复盘 | 说明做了什么、剩下什么、哪里困难，以及次日时间变化；直接修改或确认产品整理的结构化文本 | 直接展示对应到任务的结构化记录；模糊信息需校正，无需核对识别原文 |
| 漏总结后恢复 | 核对已有打卡预填的简短复盘，补充实际进度和今天可用时间 | 未打卡标为待确认；复盘确认后生成今天剩余时段的日计划草案，整份确认后保存 |
| 次日规划 | 完成今日总结后，查看任务、时段、安排依据与延期说明 | 从周任务池的剩余任务中生成符合可用时间的明日计划草案，允许调整 |
| 确认执行 | 确认整份计划 | 写入 App 内日历，设置对应提醒，明确展示保存结果 |
| 明细反馈 | 按任务打卡或语音反馈；有明确总量的部分完成任务当次填写或确认语音提取的完成数量（D20-A），未完成任务当次用文字或语音说明原因后保存（D21-A） | 语音反馈直接展示可修改的结构化文本，确认后更新任务进度、剩余量、困难及未完成原因；有明确总量时据已确认完成量计算剩余量，供下一轮复盘和重排使用 |

已确认的计划层级：

| 层级 | 内容 | 与下一层的关系 |
|---|---|---|
| 月计划 | 本月需要达成的阶段成果 | 跨月随复盘提出下月目标草案，用户修改确认后为周计划提供方向（D13-A） |
| 周计划 | 具体学习任务、工作量及剩余进度，形成待安排任务池 | 跨周时随每日复盘生成新周草案，用户修改确认后为每日排程提供任务（D12-A） |
| 日计划 | 当日具体时间段及对应任务 | 日常明日时段在完成今日总结后生成；首次按建档信息直接生成首份日程，均经确认后保存 |

月/周计划从底部独立“计划”入口进入，按 D22-A 在同页以本周任务池为主体，简要呈现本月目标。首次由产品依据建档信息生成，用户可修改并确认；后续周任务池按 D12-A 在跨周复盘后提出草案，下月目标按 D13-A 在跨月复盘时提出草案，均确认后更新。任务池不等同于预先生成未来每天的时段安排。

任务描述学习内容、完成标准与进度，日历时段描述何时执行。任务可跨时段、跨天；原日期的实际执行记录保留。学习了多久、完成了多少、是否仍有不理解的内容分别记录，不把时长或一次勾选直接当作掌握程度。

例如：计划完成 20 道练习，实际完成 12 道，另有 2 道不会。产品分别记录剩余 8 道和待解决问题，再决定次日如何安排。

D20-A 明确上述有总量任务的数量输入时机：当次记录“部分完成”时填写或确认已完成量，再计算剩余量；不将缺少数量的草稿当作数量齐全的已确认进度。没有明确总量的学习任务继续使用其具体内容和完成标准记录，不为满足此规则虚构数量。

## 5. Agent 的排程与操作规则（拟定）

- 首次根据用户提供的学习现状、相关背景、报考目标与时间约束，由产品生成月目标及周任务，用户可修改并确认；据此直接生成指定起始日的首份日计划。用户提供个人情况，产品负责提出规划。
- 日常输入共同包含月度阶段目标、周任务池、垂类策略、各科进度、任务剩余量、个人可用时间及固定事项，不能只根据昨天完成量排明天；每日排程从任务池的剩余任务中安排明日时段。
- 若复盘后要安排的学习日进入新周，先按 D12-A 根据累计进度、阶段目标和剩余任务提出下周任务池草案，用户修改确认后再生成对应日计划；用户取消周草案时保留既有已确认计划和实际历史。
- 跨月时按 D13-A 用本月实际进度和备考阶段提出下月目标草案，修改确认后指导后续周任务。跨月与跨周重合时，沿用月 → 周 → 日的依赖顺序；任何新草案都不自行替换已确认安排或历史记录。
- 漏总结后的恢复采用 D6-A：用已有打卡预填简短复盘，未打卡标为待确认；核对实际进度与今天可用时间后，只生成今天尚可执行时段的草案，日计划确认后再保存和设提醒。补录归属昨日的实际记录，不把未知状态或未确认信息当成已经完成、未完成的事实。
- 按 D15-A 根据个人可用时间与固定安排提出个人时段模板，学生调整确认后固定复用；模板规定课程表的时段，日计划规定对应学习任务。每日生成任务不自动改写已确认模板，实际可用时间变化仍须核对并确认新日计划。不安排到固定不可用时段，不让计划内部时间重叠；预计任务量超过可用时间时，提出延期或调整建议并解释原因。
- 语音反馈结束后直接展示结构化处理后的文本，用户可直接编辑并确认，确认后才保存反馈记录；无需核对识别原文，不增加单独的原文确认步骤。以用户最终确认的结构化内容作为记录依据。日期、任务或完成量存在歧义时补问，不带着歧义修改日历；“今天/明天”在确认页显示明确日期。日计划草案仍单独预览并确认后写入日历，不将确认学习反馈等同于确认新日程。
- 语音结构化反馈与已有打卡不一致时，按 D8-A 在当前可编辑的结构化内容中标出原记录和本次反馈；修改或确认后才更新对应任务，保留历史。沿用现有结构化内容确认环节，无需另设原文核对。
- 已有明确总量的任务在打卡部分完成时，按 D20-A 当次填写或从语音提取并确认已完成数量，才保存为本次已确认的部分完成记录，并计算剩余量。数量缺失、单位不清或与任务记录矛盾时，先补充或校正，不猜测数值；未确认的内容不作为排程依据。
- 学生主动打卡未完成时，按 D21-A 当次说明原因后保存。语音原因仍需在可编辑的结构化文本中确认；缺少原因时显示需补充内容并保留草稿，不将其冒充已保存记录，不据空白或未确认内容推测原因。未打卡的待确认状态不自动转换为未完成。
- 计划草案、学生确认、日历保存结果分开呈现。学生取消确认时保留原计划；保存失败时不能显示“已安排成功”。按 D9-A 保留已确认草稿、显示失败原因和“重试保存”，由用户点击后重试保存原计划；修改后的计划需重新确认。重试保存不是重新生成计划。
- 更新未来安排时保留实际历史。重复确认或重试不得生成重复时段与提醒；部分写入失败时显示具体结果并提供一致性恢复，不能静默留下半份计划。
- 手机提醒跟随确认后的安排：取消或重排时撤销旧提醒，再注册新提醒。没有提醒权限时照常保存日历，并明确显示提醒未启用。
- 调整原因可追溯，例如“可用时间减少”“该任务仍有未理解内容”“本阶段优先补齐某项内容”。初版任务估时与优先级细则仍需进一步设计。
- AI 处理按 2026-10-22 前台方案：手机先保留输入，再向云端提交当前模型所需上下文；用户留在生成页及 App 前台，查看真实阶段和适合展示的流式内容。完整结果通过结构、时间约束及与本机最新记录的差异核对后，保存为本地待确认草案；学生确认后才更新反馈、计划、日历和提醒。连接中断或离页/退后台不承诺继续处理，保留本机输入及已确认内容，显示中断供用户重试，不自动应用残片；迟到回调不得覆盖新请求或已确认记录。自有云端不设计用户输入/结果的持久任务存储、后台领取、落盘回执或 TTL 清理服务；第三方模型商处理条件仍待核验。

## 6. 学习指导与知识依据

垂类资料承担备考策略和行动建议的依据，个人档案与执行记录承担适配依据。建议需关联资料来源、适用年度或阶段、适用条件，以及与当前学生情况的关系。

经验冲突、资料过时或信息不足时，应展示不确定之处并请求必要信息。首批院系、专业、考试科目和资料版本尚未核定；对应年度考试要求需以后续官方信息核对。

原始构想中的题目级“部分学科答疑”按 D23-A 明确暂缓，不纳入首版实施。备考规划、学习情况与困难交流、学习方法建议继续保留，仍以垂类资料与个人档案、进度记录为依据；不能借此扩大为未经确认的完整学科解题能力。

## 7. 信息结构与已确认的页面路径

- **底部导航**：已确认“日历”与独立“计划”入口并列；本稿不从未定义的导航项新增功能或实施任务。
- **月历首页（日历入口）**：App 打开后的主要入口，显示本月每一天；点击今天进入今日任务页。未来尚未生成日计划的日期也允许进入，对应页面显示“尚未生成日计划”、生成时机说明和“查看周任务”入口。
- **今日任务页**：采用课程表式纵向时间轴，一天分为固定的几段时间，按顺序展示对应任务和完成情况；点击每个时段查看任务详情，并沿用具体任务的状态打卡及语音反馈（D14-B）。按 D15-A 由产品依据个人可用时间和固定安排提出时段模板，学生调整确认后固定复用，Agent 安排每日任务；具体段数与起止时间在个人模板中确定。系统字体放大时按 D18-A 让时段行随文字增高，完整显示任务名称和状态，允许纵向滚动。
- **首次规划**：收集学习现状与相关背景 → 产品生成月目标与周任务 → 用户修改并确认 → 产品提出个人时段模板 → 用户调整并确认 → 选择起始学习日 → 基于模板直接生成首份日计划草案 → 用户确认后保存日历并设置提醒。
- **今日总结与明日计划**：日常完成今日总结后才生成明日计划；整份计划经用户确认后保存到 App 日历并设置提醒。首次规划按上面的独立启动流程处理。
- **日计划保存失败**：保留已确认草稿，显示失败原因与“重试保存”；点击后保存原计划，若先修改则重新确认（D9-A）。
- **漏总结后恢复**：昨天未总结且今天无计划 → 已有打卡预填简短复盘（未打卡待确认）→ 用户核对进度与今日可用时间 → 确认复盘 → 生成今天剩余时段草案 → 确认整份日计划后保存及设提醒。
- **语音交流**：用于规划、复盘、咨询与临时修改；原音按工程 D11-A 仅在手机识别，必要文字及上下文供云端模型结构化。学习反馈结束后直接展示可编辑的结构化文本，与已有打卡不一致时在同页标出差异，用户修改并确认后保存对应记录；保留文字输入，不要求核对识别原文。本机不支持或识别失败时不上传音频补救。
- **AI 前台生成页**：提示生成期间保持 App 前台，随实际执行展示“正在整理学习信息 / 正在生成安排 / 正在检查时间约束”等阶段，可逐步展示适合用户阅读的生成内容；完整结果可编辑并需确认。离页、切后台、关闭 App 或断网后不保证继续，返回显示中断及重试路径，保留本地输入和已有记录；不显示伪进度，不自动应用不完整结果。D11-B 的仅 App 内结果提示保持，无 AI 完成手机通知。
- **计划入口**：按 D22-A 在同页以本周任务池为主体，简要呈现本月目标作为上层方向；与日历按“月度阶段成果 → 周具体任务池 → 日时段”承接。计划的生成、修改确认和跨周/月更新沿用既有规则，呈现采用已确认的原生共用角色。
- **跨周衔接**：每日复盘（含已确认的漏总结恢复）→ 待安排学习日进入新周 → 产品提出下周任务池草案 → 学生修改确认 → 生成对应日计划草案（D12-A）。
- **跨月衔接**：跨月复盘 → 产品依据本月实际进度和备考阶段提出下月目标草案 → 学生修改确认 → 用于后续周任务和日计划安排（D13-A）。
- **学习记录与复盘**：查看各日实际进度、未完成内容和阶段变化；从日历可回到对应记录。
- 档案、阶段目标与资料依据沿用相关的建档、计划与交流流程呈现。本轮已确定上述页面路径、计划层级、原生视觉基线与共用呈现规则；组件到具体框架及文件结构的映射、实际界面效果与设备验证交由后续工程实现，不再作为未回答的视觉选项。

- **工程 D11-A 已选边界**：原音仅在手机内识别，能力检查失败时不发起可能发送原音的识别请求，改用既有文字路径。可评估 Apple 本机识别接口，具体 API 及最低系统待设备信息核对；不能只设置设备端请求标志而忽略支持情况。只向云端模型发送所需文字/学习上下文，不新增原文核对页面。[Apple 本机识别能力](https://developer.apple.com/documentation/speech/sfspeechrecognizer/supportsondevicerecognition)、[要求设备端识别](https://developer.apple.com/documentation/speech/sfspeechrecognitionrequest/requiresondevicerecognition)。
- **已补充的设备事实（2026-10-22）**：用户提供“型号：iPhone 17；IOS版本：IOS26.6.1”，记录为首台真机验证设备，尚未读取设备或运行 App。官方 SpeechTranscriber 的 API 版本门槛为 iOS 26，可作为该用户报告系统上的本机转写候选；是否可用、是否支持目标中文及语言资源是否已安装，仍须运行时检查。此信息不等于将产品最低系统定为 iOS 26，也不等于中文识别或考研术语已通过测试。[SpeechTranscriber](https://developer.apple.com/documentation/speech/speechtranscriber)、[Apple SpeechAnalyzer 介绍](https://developer.apple.com/videos/play/wwdc2025/277/)。
- **平台事实**：预先排定的本地通知可由系统在 App 后台或未运行时处理呈现；通知需授权。**建议**：在计划确认并保存成功后注册提醒，展示当前权限状态。呈现仍受系统设置影响，不承诺每次必然打断学生。[Apple 本地通知与授权](https://developer.apple.com/documentation/usernotifications/scheduling-a-notification-locally-from-your-app)、[通知授权](https://developer.apple.com/documentation/usernotifications/asking-permission-to-use-notifications)。
- **2026-10-22 当前方案**：首版不依赖 iOS 后台执行或远端持久任务。App 提示保持前台，通过请求期间的流式返回展示真实阶段和可阅读内容；不能阻止用户关闭或切出 App，也不承诺切后台后继续生成。
- **内置能力优先的实现建议**：FastAPI 可用流式响应，iOS 可用 URLSession 增量读取；具体事件格式、SDK 版本与模型供应商仍待工程实现核对。必须等完整结果通过校验后，才作为本地可编辑草案；不能将流式片段冒充已保存计划。[FastAPI 流式响应](https://fastapi.tiangolo.com/advanced/custom-response/#streamingresponse)、[Apple URLSession 增量读取](https://developer.apple.com/documentation/foundation/urlsession/bytes%28for%3Adelegate%3A%29)。
- **中断与取消边界**：自有后端对断开的前台请求结束流式交付并尽力取消对应上游调用，不保存待领取结果或启动恢复队列；不承诺模型商内部立即停止或零留存，相关能力随供应商核验。手机保留输入，用户重试时视为新的前台生成，不自动应用旧流的迟到片段。

## 9. 第一阶段流程验收建议

使用一份模拟或本人历史备考档案，连续演示至少三个日期；这是建议的流程验收样例，不是已验证的使用效果。

1. 首次语音建档收集学习现状和相关背景，产品生成月目标与周任务，用户可修改并确认；随后可直接为今天剩余时间或明天生成首份日计划，确认后保存，无需先完成今日总结。
2. 语音复盘后直接展示结构化文本，用户可直接修改并确认，无需核对识别原文；确认后正确归入具体任务，保留完成量、剩余内容和困难，日计划仍需另行确认。
3. 次日草案符合可用时间和固定事项，并说明延期；确认后日历中出现对应时段。
4. 取消确认、重复提交、保存失败及部分写入失败时，计划与结果展示保持一致；保存失败时保留已确认草稿并显示失败原因及“重试保存”，点击重试不会重新生成计划、重复时段或重复提醒，修改后需重新确认（D9-A）。
5. 次日时间减少且前日未完成时，能重排并保留历史，不生成重复任务或旧提醒。
6. 无语音或提醒权限时，核心记录与日历仍可操作，缺失能力有明确状态。工程 D11-A 要求目标中文设备先核验本机识别能力；不支持或识别失败时可用文字完成流程，不把原音发送到自有后端或第三方服务作回退；无原文核对步骤。
7. 漏做昨日总结且今天无计划时，能用打卡预填简短复盘，未打卡任务显示待确认；核对今日可用时间后只安排剩余时段，确认后保存，不改写昨日历史或补排过去时段。
8. 语音结构化反馈与同一任务的已有打卡不一致时，在结构化内容中显示差异；用户可同页修改并确认，确认前不更新已有记录，确认后保留历史并采用最终确认内容。
9. 按 2026-10-22 前台方案，用户停留生成页及 App 前台时能随真实执行看到阶段/生成内容；完整结果核对后才显示可编辑确认。离页、退后台、关闭或断网后不保证继续，保留本机输入和已确认记录，返回显示中断并由用户重试；迟到片段不得覆盖新请求，流式残片不得保存为已确认计划。无 AI 完成手机通知，确认后的学习时段提醒继续设置；不再验收后台结果领取或远端持久任务。

10. 复盘后待安排的学习日跨周时，依据累计进度、阶段目标和剩余任务提出下周任务池草案；用户修改确认后再衔接日计划，取消时保留已确认计划与原周实际记录（D12-A）。

11. 跨月复盘依据本月实际进度和备考阶段提出下月目标草案，用户修改确认后指导周任务；取消时保留原已确认目标和实际记录。若跨周、跨月同时发生，月目标、周任务池、日计划按依赖顺序衔接，各自确认后应用（D13-A）。

12. 从月历点击今天后，今日任务页按课程表式纵向时间轴展示一天的固定时段及任务完成情况；点击各时段可查看对应任务详情，沿用细分完成反馈，不把时段经过或一次打卡当作掌握程度（D14-B）。

13. 产品根据建档中的个人可用时间和固定安排提出时段模板，用户可调整并确认；后续每日任务填入已确认的个人时段，模板固定复用，生成每日任务不擅自改写模板。实际时间变化及漏总结恢复仍核对可用时间，确认日计划后应用（D15-A）。

14. 针对同一组样例记录，更换共用强调色和文字层级、调整课程表时段的展示布局；月历、任务与确认页面一致采用新定义，任务内容、完成量、历史记录、已确认日程与提醒规则保持一致。检查变更涉及的文件，验证未将纯外观调整扩散到排程与数据存储逻辑（D16-A；待实现后验证）。

15. 月历、课程表时段、任务详情和反馈对颜色使用一致语义：当前选择、主要操作与完成状态采用相应的共用定义；学科通过文字识别，不依赖学科专属固定配色（D17-A）。

16. 放大系统字体并使用较长任务名称、不同完成状态检查今日课程表：行高随文字增高，任务名称和状态完整显示，页面可纵向滚动且时段可进入详情；显示高度改变不改变已确认的学习起止时间（D18-A；待实现后验证）。

17. 对“计划 20 题、完成 12 题”的任务，当次打卡部分完成时填写或确认语音提取的 12，保存后得到剩余 8；缺少数量或存在歧义时先补充、校正，不能将只有状态的草稿作为已确认数量或据此猜测剩余量。没有明确总量的任务不被强制虚构数量（D20-A）。

18. 主动打卡未完成时，当次通过文字或语音说明原因后才能保存为有效的本次反馈；语音原因在结构化文本中可修改并确认。缺少原因时提示补充、保留草稿及既有记录，不显示成已保存，也不自动编写原因。未打卡任务继续保持待确认（D21-A）。

19. 从底部进入“计划”后，同页可查看本周任务池和本月目标概要，周任务是主要内容，任务工作量与剩余进度沿用既有记录；保持与已确认月目标及日计划的层级承接（D22-A）。

20. 首版交流可处理备考规划、学习情况与困难、学习方法建议，并说明资料依据及适用条件；不将具体题目的讲解与解答纳入首版能力或验收（D23-A）。

真实用户试用与反馈在上述流程跑通之后安排。

**数据流与状态**

```text
Voice (on device) OR Text
    -> local input draft
    -> request snapshot + versions + requestID
    -> FastAPI: credential / bounds / budget admission
         -> selected provider adapter -> incremental events
    -> App owns one generation session
         stage/delta -> readable progress only
         error/EOF/cancel -> interrupted or failed; keep local input
         complete -> schema + domain + version checks
                       fail -> editable issue / retry; no application
                       pass -> persist complete local draft
                                  -> user edits / confirms
                                  -> revalidate current versions
                                  -> local commit(applicationID + records + reminder intents)
                                      fail -> same draft, manual retry-save
                                      pass -> reconcile local notifications
                                                fail -> saved plan + reminder error
                                                pass -> registered status
```

生成状态采用一个拥有者，区分 idle / preparing / streaming / validating / draftReady / interrupted / failed；用户确认与计划应用另有状态，不混成一个“成功”。离页、退后台、取消时先使当前会话无效，再尽力取消网络；所有增量、错误、完成与保存回调都核对 requestID 和当前状态。已完整保存的草案不因迟到的取消错误而丢失。

本机日期使用明确学习日期与时区，时段同时有开始/结束；“今天/明天”在预览中落为明确日期。零可用时间允许给出“无可安排时段”和延期说明，不能捏造可用时间或把未打卡自动算作未完成。

**云端接口与正文边界**

建议一个前台生成入口（例如 POST /v1/generations/stream，路径为拟议契约），operation 区分结构化反馈、月规划、周规划、日规划、学习指导；不是开放任意模型/URL 的代理。请求带 schemaVersion、requestID、必要的 snapshot/versions、可用时间及经过筛选的知识片段/引用标识，不含原音、完整无限历史或供应商密钥。响应只有真实 stage、可展示 delta、明确 complete 或 error；版本和 requestID 必须可核对。
