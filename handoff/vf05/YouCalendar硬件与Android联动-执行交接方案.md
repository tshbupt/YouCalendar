# YouCalendar 硬件与 Android 联动：执行交接方案

版本：v1.0｜整理日期：2026-11-09｜用途：交给另一台电脑、另一个账号中的执行 Agent。

**当前方向是完整 Android App＋可选 ESP-Mosaico 桌面辅助硬件。已选择先用实物跑一个真实学习时段，再单独完成 Android 联动验收。** 摄像头学习监测与多功能交互模块是硬件的特色，App 保留独立完成备考闭环的能力。

本文件可单独复制，必要背景、规则和任务已写在正文中。相关旧成果仅在第 9 节列出文件名与用途，不依赖原电脑路径、原账号会话或其私有 skill 状态。执行 Agent 若已有代码和成果，应在已有工作上增量推进。

本次交付只整理方案，没有采购、安装开发工具、编写固件或 Android 代码、调用付费服务或进行真机测试。已确认产品方向与待确认工程建议在文中分别标注。生成这份交接文件不代表所有工程细节已批准，也不将上一轮 Office Hours 设计草稿改记为整稿获批。后续按任务提交具体方案，由用户确认后实施。

## 1. 接手后先做什么

1. 阅读本文件，进行必要的只读检查，核对当前目录已有源码、文档、测试证据和工具。
2. 汇报已有能力、与本方案的差异、缺少的条件。另一台电脑的实际成果优先于本文件关于实现进度的历史快照；产品方向以用户最新明确决定为准。
3. 围绕 HW-01 提出第一项可单独交付和验收的执行方案。已有充分核验成果可直接复用，说明证据后再安排缺口。
4. 等待用户明确确认，在确认范围内完成该项工作、验证和修复。
5. 汇报结果与未完成项，提出下一项具体方案，等待确认后再实施。

### 每项任务的沟通约定

**任务前**说明问题、HW/T/ET 编号、关联成果、具体步骤与理由、预计改动文件、交付物、验证方法、完成条件、当前无法验证的条件，以及费用、依赖和数据处理取舍。任务规模以可独立验收为准，不把全部开发合并为一次批准，也不为每个普通文件或命令重新询问。

**任务中**自主完成已确认范围内的实现、测试和修复。实质改变范围、技术路线、图像处理位置、数据留存边界或费用时，先说明变化并等待确认。未回复不表示同意；当前任务的确认不自动授权后续任务。

**任务后**报告做了什么、实际验证了什么、还有什么没完成、更新了哪些状态和文档、建议下一步做什么。区分“已实现”与“已验证”，失败、未运行和等待实物的项目分别记录。汇报后暂停下一项实施。

## 2. 产品背景与当前有效决定

### 2.1 要解决的问题

目标用户是备考北邮信通院、电子院的本科生。长期、多科目备考容易出现初期迷茫和阶段性行动不明确。App 以知识库中的备考策略及个人学习进展为依据，帮助用户制定、执行、记录和调整计划。

增加硬件的目的是让学习任务独立可见，减少为查任务、计时和打卡拿起手机的次数；同时探索固定桌面摄像头与实体交互的价值。用户也希望从零到一完成一个硬件样机。第一阶段先跑通本人可用的功能闭环，之后再安排真实用户反馈。

### 2.2 已确认事项

| 事项 | 当前决定 |
|---|---|
| 客户端平台 | Android。旧文件中的 iOS、Swift/SwiftUI 和等待 Mac 的客户端要求不再作为当前实施前提；Android 语言、UI 框架和最低系统版本尚未确定 |
| 产品关系 | App 完整可用，硬件是可选辅助设备。未购买、未绑定、断连或硬件故障，不能阻断 App 基本功能 |
| 首轮路线 A | 设备预置一个真实任务，完成查看、实体操作、计时和具体打卡；完整 App 同步随后单独验收 |
| 硬件特色 | 摄像头学习监测、多功能交互模块；查看和打卡等共享能力可同时存在于 App 与硬件 |

## 3. App、硬件与云端的分工

| 功能 | Android App | ESP-Mosaico | 云端 |
|---|---|---|---|
| 建档、基础、可用时间 | 完整录入与修改 | 只接收执行所需摘要 | 按请求辅助规划 |
| 月/周/日计划 | 生成入口、修改、分别确认、完整查看 | 查看已确认并送达的任务 | 基于知识库生成草案 |
| 日历与任务 | 月历、每日纵向时段、任务详情和历史 | 当前/下一任务、简短详情，后续增加今日列表 | 基础查看不需要模型 |
| 计时与打卡 | 保留完整操作能力 | 实体开始/暂停/结束、状态、数量与快捷原因 | 不替用户判断任务完成 |
| 语音与复盘 | 主要入口，结构化内容可编辑确认 | 简短语音备注属于后续候选 | 按批准的数据方案识别和整理 |
| 摄像头监测 | 设置、查看、纠正及辅助复盘 | 固定机位采集、可见启停、状态显示 | 是否接图像尚未批准 |
| 模块特色 | 配置和查看结果 | 按键、RGB 灯、光敏、PIR；红外为后续扩展 | 基础交互不调用模型 |
| 数据保存 | 个人主记录、正式计划、确认历史 | 任务副本、持久待同步记录 | 维护知识内容和索引，处理必要请求 |

### App 必须继承的业务规则

- 首次建档后提出月目标、周任务和个人时段模板，用户修改确认后生成首份日计划。
- 月历首页点击日期进入纵向时间轴，另有独立“计划”入口承载周/月计划。未来日期可查看，未生成时明确显示空状态。
- 日常复盘后才生成明日计划；漏复盘且当天无计划时，快速补充复盘后安排当天剩余可用时段。未完成任务结合容量重排，不机械地全部搬到次日。
- 跨月、跨周时随复盘衔接月目标、周任务和日计划，各层分别确认。个人时段模板调整也需用户确认。
- 语音反馈直接呈现结构化内容供编辑，不强制先核对识别原文；与已有打卡的差异直接标出。反馈确认与新计划确认是两个动作。
- 计划经完整校验和用户确认后才正式保存并安排提醒。保存失败保留同份草稿，点击重试保存，不重新调用模型生成另一份计划。
- 首版生成过程留在 App 前台，显示真实阶段或流式内容；离页、退后台、关闭或断网不保证继续，保留可恢复的本地输入并支持手动重试，不应用残缺结果。
- 未打卡属于待确认，不能自动写为未完成。未连接设备属于没有监测数据，不能推断为未学习。
- 视觉定义和共用组件与业务隔离，以便后续更换设计。颜色表达选择、操作和完成状态，学科用文字区分。

这些规则是 App 产品目标。首轮硬件样机通过不能据此把完整 App 标为完成。

## 4. 硬件首轮范围与数据规则

### 4.1 硬件能力及使用边界

前期产品方案依据官方资料记录了触屏、音频、板载传感器，以及交互模块的两路按键/触摸输入、RGB、光敏、PIR 和红外发射。具体芯片、引脚、电气、模块修订、驱动与同时运行能力，在 HW-01/HW-02 中对照实物和官方资料重新核实。官网 `latest` 不代表收到的硬件修订号。

首轮优先完成当前任务、任务反馈、本地保存状态、必要设置和真实实体操作。完整月历编辑、长文本复盘、模型规划留在 App。红外控制外部台灯、硬件语音、多设备共用和远程云中转属于后续候选。

PIR 提供运动线索，静坐无运动不能判为无人；光敏用于相对明暗反馈，不直接宣称照度测量或护眼效果。按键/触摸两路不要当作四个独立业务输入。接线与供电以对应修订的官方说明为准。

### 4.2 路线 A 的真实任务流程

1. 先选一份本人实际要完成的学习任务，明确时间、单位、目标总量和完成标准；预置方式在 HW-01 中确定。
2. 设备上查看当前任务，通过实体输入开始、暂停或结束计时。
3. 结束后单独填写反馈。以“练习 20 题，累计完成 12 题、剩余 8 题”为典型用例。
4. 有总量的“部分完成”须在设备填写完成量；主动选择“未完成”须填写或选择具体原因。复杂补充可之后在 App 处理，必填字段缺失时只保留草稿。
5. 用户确认后设备持久保存；离开反馈页再进入，能读回相同状态、数量和原因。保存失败不能显示成功。
6. 本轮尚未接 App 时，记录显示为本地保存/未同步。后续补充 Android 联动，不把人工预置展示成自动同步。

计时结束不等于任务完成。计时、传感器事件、算法推断、用户确认的任务产出分别记录。在座不等于专注，离座不等于未学习；60 分钟计时中出现 8 分钟疑似离座，不能直接称为“有效学习 52 分钟”。首版监测仅记录或提示，不自动暂停计时、不修改任务完成量、不直接改正式计划。

### 4.3 后续联动必须落实的语义

以下是协议应表达的信息，不是已定稿的 JSON 或数据库结构。实现前与已有模型对齐，避免另造一套重复含义。

| 对象 | 必须表达的信息 |
|---|---|
| 计划副本 | 日期、时区/有效时间信息、任务身份、计划版本、时段、目标、数量单位和完成标准 |
| 任务会话 | 会话身份、关联任务、开始/暂停/结束、实际记录时长、是否因掉电中断 |
| 反馈 | 稳定事件 ID、来源、任务与计划版本、状态、数量口径、必要原因、确认状态 |
| 监测摘要 | 时间区间、算法来源/版本、推断状态、异常、用户纠正与原推断的区别 |
| 同步状态 | 本地草稿、本地已保存、待同步、已同步、冲突待处理和失败原因 |

数量采用累计值还是增量须在协议中唯一明确。上述 12/20 示例采用累计值；不能把相同累计记录相加为 24。

联动验收必须覆盖以下规则：

- **计划送达**：设备完整接收并校验后才切换版本。中途断开保留原完整计划，不能显示新计划已同步。
- **记录回传**：App 持久保存且能读回反馈后，才确认业务同步成功；传输层收到数据不算保存成功。写入失败或确认丢失，设备保留待同步事件并可重试。
- **重试与冲突**：同一事件重传只应用一次；不同会话即便数值相同也分别保留。两端分别改成 12 与 15 时保留差异，由用户决定，不能按设备时钟静默覆盖或直接相加。
- **旧任务**：计划变更、任务删除后回传的记录仍保留原关联，进入可解释的处理流程，不悄悄丢弃或套用到新任务。
- **断电与时间**：已显示保存成功的记录重启可恢复；计时中途掉电标为中断，不补算离线时长。时间不可信时提示校时，不假定板载电池保证时钟正确。
- **手机不在**：有供电、有效时间和本地任务时，设备继续查看、计时和记录；缺少当天计划则明确显示，不冒用昨日安排。
- **绑定与关闭**：只允许已绑定端修改计划；解绑和转交前明确待同步数据的处理。App 发出监测关闭指令，设备尚未确认前显示待送达，不能宣称相机已经停止。
- **提醒**：手机和设备提醒状态分别可见，不因曾连接过硬件就自动取消手机提醒；去重策略在交互方案中说明。

## 5. 分阶段任务与验收

本节保留已有 HW-01～HW-07 编号。每项可按依赖细分为有明确交付物的小任务，但继续关联原编号。所有实现状态需由接手 Agent 核对实际代码与证据，本文件不预先勾选完成。

推荐顺序为 HW-01 → HW-02 必要基础 → HW-04 真实桌面样机；相机采集可用后尽早开展 HW-03。HW-03 与 HW-04 在各自范围获准且依赖具备时可并行推进。HW-05 是之后的 Android 联动，HW-06 依赖监测和联动结果，最后进入 HW-07。

### HW-01：已有成果、环境、实物与首轮方案

**工作**：核对当前目录、代码进度、Git/测试状态、Windows 工具、Android 工程、可用手机型号/系统/调试安装条件。用户曾报告有小米 13 国行和 iPhone；本轮目标机与系统版本仍以实际检查为准。核对设备是否已购、实际主板/模块修订、套装内容、电源、线材、支架和含运费总价。

**交付**：一份接手核验记录，列出可复用模块、缺件、工具与版本、预算、真实任务预置方式，以及下一项具体实施方案。明确 SDK/BSP 候选能否支持该修订，不把仓库存在当作已构建成功。

**完成条件**：每项环境和能力都有“已核验/用户报告/未知”的标注，缺口不靠猜测填充；下一任务可明确批准。此任务不要求买到全部设备才允许提交结果，缺实物须列为后续验证依赖。

**任务关联**：相关 T/ET 的环境与现状核对，不等于完成任何 App 功能。

### HW-02：外设与供电基础

**工作**：在授权环境中复用官方示例，验证显示、触摸、交互输入、灯光、光敏、PIR 和相机采集，记录版本、安装方向与供电；先验证 HW-04 和 HW-03 必须依赖的外设。相机出图与监测算法效果分开。

**交付**：可复现构建/烧录说明、固件和版本记录、逐外设结果与故障清单。尚未验证的外设继续保持待验证。

**完成条件**：目标板上看到实际显示和输入反馈，必要外设可用；只有构建成功时，状态只能写“已构建，待板端验证”。

**任务关联**：ET7 真机证据、ET8 资源测量；HW-02 是新硬件增量。

### HW-03：摄像头可行性实验

**工作**：实施前提出计算位置、候选算法与兼容证据、采样和图像处理路径、人工标注方式、测试规模及通过线。优先评估本地即时处理，保存事件和标注摘要；如需留原图或传到电脑、手机、云端，明确范围、位置、期限和删除方式后再实施。

**交付**：对照标注的结果报告，分别统计在座/离座误报和漏报、切换延迟、不确定占比、场景分布与测试时长，以及界面和通信同时运行时的内存、响应和稳定性。涉及网络时另记上传量、延迟与费用。

**完成条件**：按事先确认的通过线得出可用、有条件可用或不可用结论。没有预设通过线的探索实验只报告观察结果。Windows 算法成功不代表板端已通过；若板端不可行，提交调整范围或计算位置方案，不悄悄删去监测特色。
