# YouCalendar：ESP-Mosaico 辅助硬件产品方案

版本 v0.2｜更新于 2026-11-09｜首轮样机路线与客户端平台已确认，待工程细化评审。

**产品定位已明确：完整的学习规划 App＋可选的桌面辅助硬件。App 保留完整功能；硬件提供便利的执行入口，并通过摄像头和多功能交互模块增加特色能力。**

用户已选择路线 A，用 ESP-Mosaico 跑一段真实学习任务，优先验证桌面使用价值。客户端基于 Android 开发，完整联动在真机样机之后单独验收。本文可单独交接。采购、工具安装、开发及实测按各项具体方案确认后进行。

## 1. 产品目标与使用人群

首批面向备考北京邮电大学信息与通信工程学院、电子工程学院的本科生。备考涉及多个科目、持续数月，产品帮助学生建立方向、明确下一步行动，并记录和反思执行情况。

App 承担完整备考闭环：建档 → 月／周目标与个人时段模板 → 日计划 → 执行与具体任务反馈 → 每日复盘 → 下一学习日安排。知识库提供备考策略依据，用户的基础、可用时间和进展用于适配；模型提出建议，用户修改或确认后应用。

增加硬件的两个出发点：

- 学习时将任务放在独立、可见的桌面设备上，减少拿手机查看和操作的次数。
- 从零到一完成硬件样机，通过摄像头、传感器和实体交互探索 App 单独使用时没有的桌面体验。

第一阶段验证功能闭环与实际桌面体验，不据此声称提分、提高专注力或具有市场付费需求。真实用户试用仍安排在功能闭环形成之后。

## 3. App、硬件与云端的功能关系

下表描述目标能力，不代表当前代码已经实现。

| 能力 | App | 辅助硬件 | 云端 |
|---|---|---|---|
| 建档、可用时间、固定安排 | 完整录入与修改 | 可显示必要摘要 | 按请求协助理解或规划 |
| 月／周／日计划 | 生成入口、完整查看、修改和分别确认 | 查看已确认、已同步的任务 | 检索知识并生成草案 |
| 日历与任务详情 | 月历、每日时间轴、历史与详情 | 当前任务、下一任务、今日列表和简短详情 | 无须参与每次查看 |
| 计时、开始／暂停／结束 | 保留相应操作能力 | 提供实体操作和桌面显示 | 无须参与基础操作 |
| 具体任务打卡 | 完整状态、数量、原因及修改能力 | 简单状态、数量和快捷原因，用户确认后保存 | 不根据传感器直接认定完成 |
| 语音反馈、复盘交流 | 首版主要入口，结构化内容可编辑确认 | 后续可评估简短语音备注／快捷打卡 | 按已确认方案进行识别、整理和建议 |
| 摄像头监测 | 设置、查看结果、纠正判断、辅助复盘 | 固定桌面机位采集和监测入口 | 是否参与图像分析待决策 |
| 多功能交互 | 配置规则、查看结果；保留共享操作入口 | 按键、灯光、环境明暗与运动感知等 | 基础交互无需模型 |
| 统计与反思 | 完整展示，区分计时、监测和任务产出 | 显示今日简要进度 | 根据必要上下文提供建议 |
| 设备管理 | 绑定、同步、设置与更新入口 | 显示连接、同步、监测、供电状态 | 远程设备服务暂未定案 |

硬件断开、损坏或未绑定时，App 的规划、查看、打卡、复盘和统计不受功能性限制；硬件监测的数据缺失要显示为“无监测记录”，不能推断为未学习。

### 3.1 保留原有 App 的关键交互

- 月历首页进入当日纵向时间轴，月／周计划仍有完整入口；个人时段模板与每天具体任务分开。
- 首次建档后可直接生成首份计划。日常明日计划在今日复盘后生成；漏复盘且当天没有计划时，先快速补充复盘，再安排当天剩余可用时段。
- 跨周、跨月时随每日复盘提出下周任务或下月目标，允许用户修改并分别确认；同时跨月与跨周时按月目标 → 周任务 → 日计划的顺序衔接。未来日期允许进入查看，尚未生成日计划时明确显示未生成，不预填虚构任务。
- 语音反馈直接展示结构化内容，用户修改确认；确认学习反馈与确认新日计划是两个动作。
- 已确认计划才进入正式日历并安排提醒；失败、重试和部分结果不能显示为成功。
- 模型生成沿用首版前台进展展示；关闭 App 或中断后不承诺继续生成，不应用残缺输出。
- 设备产生的观测只补充复盘依据，不能绕过用户确认自动改写正式计划。

## 4. 硬件的产品形态与建议功能

设备放在书桌上，采用 USB 常供电。以当前任务和简短操作为中心，避免把 App 的全部页面缩小搬到屏幕上。

官方资料列出 2.16 英寸、480×480 触屏，板载音频、麦克风、扬声器、振动马达、IMU、磁力计、存储和无线连接能力。这些是实现条件，具体功能仍需开发。[主板用户指南](https://docs.espressif.com/projects/esp-dev-kits/zh_CN/latest/esp32s31/esp-mosaico/user_guide.html)

### 4.1 共享功能的桌面入口

| 建议首版功能 | 行为要求 |
|---|---|
| 当前任务 | 显示日期、时段、学科文字、任务目标、完成标准及当前进度；长内容分页或滚动 |
| 今日列表／下一任务 | 可查看已同步的今日安排，不把周任务池当作已生成的未来日程 |
| 开始／暂停／继续 | 用户明确操作后改变计时状态；计时名称不宣称代表有效学习时长 |
| 结束与打卡 | 结束计时后显示任务反馈，不把“结束”直接等同于“全部完成” |
| 提醒 | 屏幕、灯光及可选声音／振动；可调整或关闭，提醒方式需实机评审 |
| 同步与监测状态 | 清楚显示计划日期、最后同步时间、待同步数量、监测是否开启及是否异常 |

有总量任务选择“部分完成”时，当次填写完成数量；主动选择“未完成”时，当次选择或填写具体原因。硬件可提供“时间不足”“不会做”“临时安排”等快捷原因，复杂说明可再由 App 补充。缺少必需数量或原因时只保留待补充草稿，不能冒充完整已确认打卡。

示例：计划做 20 题，本次确认累计完成 12 题，剩余 8 题；“另有 2 题不会”作为困难记录，不自行改变已完成数量的含义。数量单位及累计／增量口径要在实现前统一，两端不能重复累加。

### 4.2 多功能交互模块的特色

模块具备两路按键／触摸输入、RGB 灯、光敏电阻、PIR 运动感知和红外发射能力。按键与触摸并非四个独立输入，应按实际电路选择和验证。[交互模块指南](https://docs.espressif.com/projects/esp-dev-kits/zh_CN/latest/esp32s31/esp-mosaico/user_guide_interact.html)

| 能力 | 建议功能 | 优先级及限制 |
|---|---|---|
| 实体按键／触摸 | 开始／暂停、进入结束确认、切换简要视图 | 首版；具体映射待交互评审，不占用 BOOT／POWER 作为默认业务键 |
| RGB 灯 | 用低亮度、简短变化提示任务状态和休息开始 | 首版；颜色与屏幕状态含义一致，不按学科任意换色，不持续制造干扰 |
| 光敏电阻 | 随环境明暗调整显示或状态灯亮度 | 首版验证；只是相对明暗信号，不直接宣称准确照度或护眼效果 |
| PIR | 活动触发唤屏，提供辅助运动线索 | 首版验证；静坐无运动不等于无人，不单独据此暂停计时 |
| 红外发射 | 后续控制协议兼容的台灯等设备 | 后续；需核对目标设备协议和范围，不承诺学习任意遥控器 |

板载麦克风可在后续扩展语音快捷记录，IMU 可探索移动唤醒等操作；这些不替代 App 语音功能，也不应挤占摄像头与核心交互的验证工作。

### 4.3 建议的屏幕与交互结构

建议首版包括“当前任务”“今日任务”“任务反馈”“监测状态”“连接与设置”五类视图，按实际尺寸验证中文字号、点击区域、内容长度与误触。

当前任务示意：

```text
11 月 4 日        已同步
09:00—10:30  高数
完成指定练习 20 题
当前记录：12 / 20

[开始／暂停]   [结束与反馈]
下一项：专业课章节复习
监测：开启／暂停／不确定
```

这是信息结构示意，不是已批准的最终布局或真实屏幕效果。硬件保留当前任务的查看入口，完整计划修改和长文本编辑继续在 App 提供。

## 5. 摄像头学习监测方案

摄像头是硬件特色验证的核心任务之一，应在基础显示和外设可用后尽早实验，与任务执行功能并行推进。不能先做完所有功能，再把“摄像头能否形成有效监测”留到最后。

### 5.1 第一轮建议验证什么

建议将首个监测目标限定为单人固定桌面场景中的三种状态：**疑似在座、疑似离座、不确定**。评估状态区间、切换时间及持续时间能否为复盘提供有用线索。

以下是待验证能力，尚未有相应模型或效果证据：

- 人进入或离开主要学习位置后的状态变化。
- 光照变化、低头写字、侧身拿书、遮挡和旁人经过时的判断。
- 监测异常或视野失效时输出“不确定”，而不是强制判在座／离座。
- 用户查看并纠正监测区间，保留原始推断与纠正结果的区别。

不将“在座”解释为注意力集中，不以看见手机推断用途，不把相机记录自动换算为做题量、知识掌握、学习效率或完成状态。

### 5.2 监测数据怎样使用

四类记录分别保留：

| 记录 | 来源 | 作用 |
|---|---|---|
| 任务计时 | 用户开始、暂停、结束 | 描述用户记录的任务会话 |
| 传感器事件 | PIR 等硬件采样 | 提供运动等观察线索 |
| 监测推断 | 图像或组合信号算法 | 给出可能的在座／离座／不确定区间 |
| 已确认任务进度 | 用户打卡、修改与确认 | 表达任务完成数量、剩余内容和困难 |

例如，计时会话为 60 分钟，其中有一段 8 分钟疑似离座，应展示为独立信息；不能直接声称“有效学习 52 分钟”。用户可以确认是否确实离座、是否需要修正自己的计时记录。未经确认的推断不自动减少进度或改变任务状态。

首版建议先记录或提示疑似离座，不自动暂停计时。是否支持自动暂停，需根据误判结果再单独决定。

### 5.3 算法在哪里运行

| 候选位置 | 价值 | 必须验证的限制 | 当前建议 |
|---|---|---|---|
| ESP-Mosaico 板端 | 手机不在时也可独立监测，可减少图像传输 | 算法兼容性、准确性、内存、延迟、与界面和通信并行的稳定性 | 优先做轻量算法可行性实验；尚未选定算法 |
| 手机 App | 可借用手机计算能力 | 图片传输开销、手机在场及后台限制；可能削弱放下手机的体验 | 备选评估，不默认成为持续监测依赖 |
| 云端视觉 API | 可利用外部视觉能力 | 图片处理边界、网络、延迟、连续费用和服务留存条件 | 待明确确认，不默认接入 |
| Windows 电脑 | 便于前期采样、算法比较和调试 | 结果不能证明算法已在 MCU 上运行，也不代表最终可脱离电脑 | 仅作为开发验证手段 |

若板端不能达到约定指标，应提交真实结果，再讨论其他计算位置、调整监测范围或更换硬件；不能悄悄删除核心监测功能后仍宣称本方案完整实现。

### 5.4 摄像头使用与摆放

- 建议监测由用户明确启动，并可在硬件上直接暂停／关闭；开启状态持续可见。是否跟随学习会话自动启停，待交互确认。App 更改设备监测开关后，在设备确认接收前显示待同步，不能把尚未送达的关闭指令显示为已停止采集。
- 首版优先评估只保存事件摘要，不默认长期保存原始图片或录像；实验采样的范围、保存位置、期限和删除方式需在实验方案中说明。
- 图片传到手机或云端前需明确具体数据流；不得以语音服务已允许为由自动上传图像。
- 支架需同时满足任务查看和镜头视野；实测坐姿、书本遮挡、逆光、夜间台灯及多人经过。
- 官方要求摄像头接左侧 H2；同时使用交互模块时，可按其指南安装到右侧 H1。装配方向和具体模块版本要核对。[摄像头指南](https://docs.espressif.com/projects/esp-dev-kits/zh_CN/latest/esp32s31/esp-mosaico/user_guide_camera.html)

## 6. 完整使用流程

### 6.1 没有硬件

用户只使用 App，完成建档、计划、任务执行与打卡、复盘和统计。设备入口不得阻断主流程，硬件购买或绑定不作为基本功能使用条件。

### 6.2 使用硬件的一天

1. 晚间在 App 汇总已有打卡，进行语音或文字复盘，修改并确认结构化反馈。
2. App 请求基于知识库和个人情况生成后续计划，用户确认后保存在手机；再同步给硬件。
3. 次日硬件显示已同步的当前任务；用户可以通过实体操作开始计时，并按设置启用监测。
4. 学习中查看下一任务、暂停或休息；灯光和屏幕提供简短反馈，监测记录与计时独立保存。
5. 结束时由用户确认完成状态、数量和原因，保存到硬件待同步队列；也可以选择在 App 完成同样操作。
6. 再次连接 App 后回传记录，处理两端差异；App 展示执行和监测信息，辅助当晚复盘。

### 6.3 常见中断

- 手机离开或 App 关闭：硬件继续使用已同步内容；新计划和记录回传等下次连接。
- 当天没有已同步计划：明确显示缺少计划，不把昨日任务冒充今日安排；用户仍可在 App 处理规划。
- 任务超时但未结束：提醒用户选择继续或结束反馈，不自动认定完成，也不自动改排后续日程。
- 摄像头关闭或不确定：基础查看、计时和打卡继续可用；报告监测缺失，不补造记录。
- 网络中断：已有本地任务仍可执行；云端生成和识别按实际依赖显示不可用。

## 7. App 与硬件的联动架构建议

建议第一版采用“App 前台主动同步＋硬件本地执行”。蓝牙 BLE 是优先验证的同步通道；同一局域网 Wi-Fi 为备选。远程云中转暂不作为首版必要条件，因为它会增加服务、费用和个人数据处理边界。

```text
云端知识服务／语音服务／大模型 API
                ↕ 当前请求所需数据和结果
App：完整产品功能、个人主记录、计划版本、复盘
                ↕ 候选 BLE：已确认计划／执行及监测摘要
ESP-Mosaico：任务副本、桌面操作、监测、待同步记录
```

BLE 及具体协议待核定。若选 BLE，在目标 Android 手机和实际系统版本验证扫描、连接权限、拒绝与撤销授权、断连重试。首版以用户打开 App 时主动同步为验收范围。[Android 蓝牙权限](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions)

### 7.1 数据保存与同步规则

| 对象 | 建议位置与规则 |
|---|---|
| 档案、正式计划、学习历史 | App 本地为主记录；完整备份／迁移按已有 App 方案处理，本文件不新增云备份承诺 |
| 设备任务副本 | 只同步执行需要且已确认的计划，带日期、任务 ID 和计划版本 |
| 硬件打卡与计时 | 本地持久保存，带事件 ID、任务 ID、关联版本及来源。App 保存成功并可读回后才确认同步，硬件据此按保留规则清理 |
| 监测摘要 | 保留来源、时间区间、推断状态和纠正状态；原始图像留存另行决策 |
| 云端知识 | 保存审核后的知识资料和索引；与个人学习主记录区分 |
| 云端智能请求 | 只提交当前处理必要的数据；服务端与供应商的日志、地区、留存条件需核验 |

建议首版一名用户绑定一台设备。协议需限制未绑定端修改计划；解绑、重新绑定和设备转交时，明确本地记录如何同步、导出或删除。多用户共用和一人多设备不默认进入首版。

同步必须满足：

1. **保存和送达分开。** App 已保存但设备未确认时显示“待同步”，设备只在完整接收并校验后切换计划。
2. **重复上传不重复记账。** 同一事件在断连后重试只应用一次。不同时段的事件分别保留，即便记录的完成量相同，累计数量仍按任务规则核对。
3. **保留两端冲突。** 同一任务在 App 和硬件有不同数量、原因或状态时，App 展示差异并由用户确认；不凭设备时钟简单覆盖，也不无条件相加。
4. **计划更新保留历史。** 旧任务已执行的记录仍关联原任务；任务被删除或改动时，相关回传记录进入可解释的处理流程。
5. **时间有效才按时提醒。** 正常运行用合适的计时方式；断电重启后若时间不可确认，显示需要校时，不能假设板载电池保证日历时钟持续正确。学习会话中途掉电时标记中断，不把断电期间补算为学习时长。
6. **同步中断可恢复。** 已确认记录、待补充草稿、待同步事件分开，存储失败或空间不足时明确提示，不能显示保存成功。

App 与硬件的提醒可以分别设置；首版不因设备曾经连接就默默关闭手机提醒。需要减少双端重复提醒时，在交互评审中明确用户可见的规则。

### 7.2 复用方向与工程条件

- 硬件优先使用乐鑫官方 BSP、外设示例及与实际板卡匹配的驱动，不从零重写显示、音频或相机驱动。SDK/BSP 的可用版本在环境核验时固定。[官方 BSP](https://github.com/esp-mosaico/esp-mosaico-bsp)
- App 复用现有的任务、数量、确认、持久化与提醒规则；硬件同步应作为新增输入来源，避免复制出含义不同的第二套业务规则。
- 知识检索及模型规划继续复用已有后端方向；硬件基础执行无需为每次按键请求模型。
- Windows 可用于固件开发、协议测试和模拟界面；最终独立执行能力必须在设备上证明。
- Android 构建和真机调试可在 Windows 环境进行。HW-01 先核对已有工程、工具及调试条件，HW-05 再在真实 Android 手机和 ESP-Mosaico 上验证联动。模拟与真机结果分别记录。[Android Studio 安装](https://developer.android.com/studio/install)、[Android 真机调试](https://developer.android.com/studio/run/device)

## 10. 验收与证据要求

### 10.1 产品与数据完整性

| 场景 | 建议通过条件 |
|---|---|
| 未绑定／断开硬件 | App 完整流程仍可操作，监测缺失不影响手动记录 |

### 10.2 监测效果

先记录人工标注的真实状态，再与算法输出比较。测试至少覆盖正常就坐、低头书写、侧身拿书、短暂离开、长时间离开、返回、镜头遮挡、弱光／逆光和旁人经过。

报告包含：在座与离座各自的误判／漏判、状态切换延迟、不确定区间占比、测试总时长、场景分布，以及同时运行显示和通信时的内存、响应和稳定性。若包含网络分析，另列上传量、延迟和实测费用。

**当前不设未经讨论的“准确率 95%”等承诺。** HW-03 实施前需约定测试规模、容许误报次数、切换延迟和不确定比例等通过线；没有预定通过线的探索实验，只能报告观察结果，不能判产品监测已验收。不能用传感器输出帧率替代算法准确性或应用吞吐。

### 10.3 实际使用价值

首轮以本人当前的手机查计划和打卡方式为基线，在相近的实际学习时段体验 ESP-Mosaico。记录为了查计划或打卡拿手机的次数、是否切到其他应用，以及是否要回手机补录数量或原因。Android App 到位后，再以 App 单独使用作为联动阶段的对照。

相机达到 HW-03 约定的基本可用条件后，在相近任务中对比监测关闭和开启。分别记录误报造成的中断，以及有没有一条监测记录促成具体的复盘或次日安排调整。未达到条件时，交付监测实验结果与当前限制。

这属于个人样机评估；不以少量使用记录推导提分、专注改善或普遍市场效果。通过标准在 HW-07 开始前确认。

证据分级：文档核对、构建、模拟协议、板端实测、真实 App 联动、连续使用分别记录。测试报告写清硬件修订、固件／App 版本、手机型号与系统、场景、结果及未覆盖项。
